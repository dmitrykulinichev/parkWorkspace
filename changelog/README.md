# Changelog — правила ведення (для агентів)

Це накопичувальний журнал змін проєкту Garage24 (суперпарк + лендінг + мобільні
застосунки). Ведеться щодня, по факту виконаної роботи.

## Навіщо цей лог

1. **Історія змін для команди** — що і коли зроблено, без потреби копатись
   у `git log`/коміт-повідомленнях кількох окремих репозиторіїв (суперпарк,
   лендінг, мобільний застосунок — усі різні git-репозиторії).
2. **Сировина для статей на лендінг** (`/blog`) про розвиток продукту — тому
   кожен запис має "стояти сам по собі" й бути зрозумілим не лише тому, хто
   писав код, а й людині, яка потім писатиме з нього маркетинговий текст.

## Структура

- Кожен день — окрема папка `YYYY-MM-DD/` (наприклад `2026-08-11/`).
- Усередині — до 4 файлів, по одному на кожну частину системи, **де сьогодні
  дійсно щось змінилось**:
  - `backend.md` — суперпарк, Laravel/API (`app/park-react-spa`)
  - `frontend.md` — React SPA (адмінка суперпарку)
  - `landing.md` — маркетинговий сайт (`landing/www`)
  - `mobile.md` — мобільний застосунок (`mobile/app`, `mobile-user/app`)
- **Не створювати файл, якщо в цій частині сьогодні нічого не змінювалось.**
  Порожніх/заглушкових файлів бути не повинно.
- Якщо робота над тим самим триває кілька днів — новий день все одно отримує
  свою папку; якщо продовжується робота **того ж дня** (кілька сесій) —
  дописувати в наявні файли дня, а не створювати дублікати чи перезаписувати.

## Формат одного запису

```markdown
## Назва зміни/фічі — коротко, по суті

Що змінилось, навіщо (яку проблему вирішує чи яку можливість додає), і, якщо
важливо для розуміння, як (ключовий механізм — не деталі реалізації, не
списки файлів, не диффи). 2-5 речень.
```

- Заголовок `##` — назва зміни, зрозуміла без контексту розмови, в якій вона
  народилась.
- Пишемо **фактично, конкретно, без води** — але й без надлишкового технічного
  жаргону чи внутрішніх деталей реалізації (назви класів/методів — можна,
  якщо це справді ключове; список усіх змінених файлів — ні).
- **Жодних секретів**: ключів, токенів, паролів, внутрішніх URL з реальними
  значеннями. Цей лог згодом стає джерелом для публічного тексту — пишемо так,
  ніби це вже майже стаття.
- Мова — українська, минулий час ("додали", "виправили", "перенесли").

## Коли додавати запис

- Після завершення функціональної зміни (фічі, значного фіксу, зміни
  архітектури) — не для кожного дрібного кроку чи проміжного коміту.
- Дослідження/рев'ю **без змін коду** — не логувати, якщо не мали суттєвого
  наслідку для рішень команди (виняток: якщо дослідження явно підтвердило
  "цього НЕ треба робити" і це рішення варте фіксації — короткий запис
  доречний).
- Один запис = одна закінчена, самодостатня зміна. Кілька дрібних пов'язаних
  правок в межах однієї фічі — один запис, не кілька.
