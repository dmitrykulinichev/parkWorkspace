# Маркетинг g24.com.ua — активний пошук клієнтів

Сегмент: власники малих таксо- та орендних парків (3–10 авто): Київ + обласні центри (з Полтавою; наш полтавський клієнт на OLX не рекламується), облік вручну.
Мета першого етапу: ~15 розмов з власниками і 3–5 парків, заведених руками, щоб зрозуміти, що болить і чому не реєструються. Продажі пізніше.

## Структура

```
registry/            — РЕЄСТР: єдине джерело правди, спільне для всіх напрямів
  clients.csv        — один рядок = один потенційний клієнт (поточний стан)
  contacts.csv       — історія контактів: один рядок = одна взаємодія (тільки дописуємо)
  seen.csv           — журнал УСІХ переглянутих власників (і відсіяних): ключ_джерела, коли бачили, рішення
  REGISTRY.md        — ЧИТАТИ ТУТ: людська версія реєстру (зведення, справи на сьогодні, історія, ліди за містами).
                       Генерується `registry/render_md.py` (автоматично після кожного merge). Вручну не редагувати.
  KARTA.md           — КАРТА БОЙОВИХ ДІЙ: лише ліди в роботі — воронка, справи на сьогодні, повна історія кожного ліда
                       (усі спроби, способи, результати, коментарі). Генерується тим самим render_md.py.
  BOLT.md            — ПАРКИ, ЩО ПРАЦЮЮТЬ З BOLT (для партнерства з Bolt): маркетплейс Bolt / лише Bolt / Bolt + інші;
  bolt_parks.csv       таблиця тих самих записів. Генерує registry/bolt_list.py (з render_md.py), тож оновлюється сам
  licenses_taxi.csv  — ЛОКАЛЬНА КОПІЯ РЕЄСТРУ ЛІЦЕНЗІЙ НА ТАКСІ (усі чинні ліцензіати: авто 2022, область, новачки, client_id,
                       можливі збіги). Генерує prospecting/methods/licenziyi-taksi/build_table.py
  log_contact.py     — одна команда записати дію з лідом: журнал contacts.csv + стадія/дата в clients.csv + перегенерація
                       (пізніше, коли флоу усталиться, — окрема сторінка в «Суперпарку»)
prospecting/         — МОДУЛЬ 1: пошук → додає клієнтів у реєстр
  AGENT.md           — інструкція модуля
  sources.md         — критерії ліда, беклог джерел, журнал прогонів
  methods/           — КАТАЛОГ МЕТОДІВ ЗБОРУ: кожен метод = опис + код, повністю відтворюваний
    README.md        — список методів і шаблон нового методу
  _raw/              — сирі вивантаження з датою (не редагуються)
tasks/               — ПОТОЧНІ ЗАДАЧІ ДЛЯ ВЛАСНИКА: що зробити руками зараз (кому, куди, готовий текст).
                       README.md — список відкритих; зроблені → tasks/done/. ПОЧИНАТИ ДЕНЬ ЗВІДСИ
changelog/           — ЖУРНАЛ РОБОТИ З ЛІДАМИ по днях: YYYY-MM-DD/{prospecting,outreach,registry,research}.md
                       (що зробили, цифри, рішення власника). Правила — changelog/README.md. Дописувати щодня.
competitors/         — БАЗА КОНКУРЕНТІВ (окремо від клієнтів): competitors.csv + README.md (як знаходили, висновки,
                       позиціювання g24). Хто з клієнтів чим користується — у `нотатки` реєстру та в полі `звʼязок_з_реєстром`
outreach/            — МОДУЛЬ 2: контакт → готує повідомлення, веде історію в реєстрі
  AGENT.md           — інструкція модуля
  scripts.md         — шаблони повідомлень і follow-up
```

Пошук наповнює реєстр, а контакт працює з тим, що в ньому вже є. Інших списків клієнтів, чернеток чи історій окремо від реєстру немає: чернетки повідомлень теж ідуть у `contacts.csv` (`тип=чернетка`).

## Правила реєстру

**clients.csv** (розділювач `;`, UTF-8 з BOM, відкривається в Excel)
- `id` — 3 цифри, присвоюється один раз і не змінюється. Новий клієнт отримує max(id)+1.
- `ключ_джерела` — стабільні ідентифікатори власника в джерелах, через пробіл (`olx:<user_id> workua:<id>`), щоб повторні прогони й інші джерела не дублювали клієнтів. Збіг між різними джерелами (за телефоном/назвою) підтверджуємо вручну, тоді дописуємо ключ.
- `місто`, `джерело` (яким методом знайдено вперше), `пріоритет` (A/B/C, правила — у method.md відповідного методу).
  Реєстр **один і без відсіву**: це заодно дослідження ринку. C = великий парк чи орієнтир (не наш клієнт, але показує ринок):
  стадія «перевірено», без дати, тож у щоденні справи не потрапляє. Фільтр за кількістю авто чи водіїв робимо пізніше.
- `телефон` — усі публічно видимі номери власника, `+380XXXXXXXXX` через кому. Склейка між джерелами йде спершу за телефоном, потім за назвою.
- `власник_id` — записи зі спільним телефоном = один власник (мережа, кілька міст чи майданчиків). Рахує `registry/link_owners.py`
  (запускається з `render_md.py`). Рядки не видаляємо, id не змінюємо.
- `де_рекламується` — усі майданчики, де бачили цього власника, з містами (`OLX прокат (Київ); Work.ua (Київ, Львів)`).
  Кожен merge дописує сюди свій майданчик, навіть якщо власник уже був у реєстрі, а в `нотатки` додає відмітку з датою.
- `перевірено = так` лише тоді, коли є `url_оголошення` на конкретне оголошення і `телефон` або інший прямий канал (чат OLX, Viber/Telegram), і хтось реально це бачив.
- `стадія` — одна з:

| стадія | значення |
|---|---|
| не перевірено | є лише назва чи гіпотеза, контакту немає |
| перевірено | є реальне оголошення і телефон, можна писати |
| написав | перше повідомлення надіслано |
| відповів | є будь-яка відповідь |
| розмова | був дзвінок або змістовне листування про їхній облік |
| онбординг | заводимо їхні авто й водіїв у g24 |
| активний | користується системою |
| платить | платить |
| відмова | закрито; причину пишемо в `нотатки` і `contacts.csv` |
| не цільовий | великий парк, не таксі, дубль тощо |

- `наступна_дія` + `дата_наступної` (YYYY-MM-DD) заповнені завжди, якщо стадія не фінальна. Щоденний список справ = рядки з `дата_наступної <= сьогодні`.

**contacts.csv** — журнал ведення ліда: **кожна** дія окремим рядком, нічого не видаляємо і не переписуємо.
Фіксуємо всі спроби, зокрема невдалі (не взяв слухавку, номера немає у Viber, не доставлено), спосіб і результат.
Записуємо командою `python -I registry/log_contact.py <id> <тип> <канал> <результат> --text "…"`: вона дописує журнал,
оновлює стадію й дату наступної дії ліда і перегенеровує REGISTRY.md (деталі — у docstring скрипта).
- `дата` YYYY-MM-DD · `client_id` · `канал` (viber / telegram / дзвінок / sms / olx-чат / email / зустріч, можна з номером)
- `напрям`: `вих` (ми) / `вх` (вони) · `тип`: чернетка / перше / follow-up / спроба / відповідь / розмова / демо / відмова
- `зміст` — коротко, що сказали · `результат` · `наступний_крок`
- Після кожного запису оновлюємо в `clients.csv` поля `стадія`, `наступна_дія` і `дата_наступної`, а потім запускаємо `python -I registry/render_md.py`.

## Ритм
- Щодня: близько 10 нових перевірених лідів, перші повідомлення, follow-up за датами (на 3-й і 7-й день, після цього стоп).
- Щотижня: воронка (скільки на кожній стадії, конверсії між ними), що працює, що змінити.
