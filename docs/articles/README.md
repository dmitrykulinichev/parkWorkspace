# Підготовка статей для блогу — правила (для агентів)

Цей файл — інструкція, як готувати статті для `/blog` на лендінгу, вироблена
на практиці під час першого масового наповнення блогу (серпень 2026, після
місячної паузи в публікаціях). Мета — щоб наступного разу не доводилось
заново винаходити процес.

Див. також: [`workspace/changelog/README.md`](../../changelog/README.md) —
ченджлог веде записи саме як "сировину для статей", тому це перше місце,
куди варто зазирнути.

## Звідки брати факти (у порядку пріоритету)

1. **`workspace/changelog/YYYY-MM-DD/*.md`** — якщо зміна досить свіжа, щоб
   потрапити туди, це вже готовий, стислий, клієнтським тоном записаний факт.
   Найшвидше й найнадійніше джерело.
2. **`workspace/user-docs2/publish/**`** — куратована документація фіч
   (за модулями: drivers/finance/fleet/park/uklon/...). Написана для
   користувачів веб-адмінки, тому дає реальні деталі поведінки й термінологію
   — навіть якщо стаття про мобільний застосунок, тут можна перевірити, як
   саме називаються сутності/поля.
3. **`mobile/app/whatsnew/*.txt`** — реліз-ноути мобільного застосунку, вже
   клієнтським тоном, з датами релізів. Дуже цінне джерело саме для мобільних
   статей, коли git-історія тонка.
4. **Сирий код** (бекенд-контролери/моделі, мобільні екрани) — коли
   документація не покриває тему або треба підтвердити деталь. Читати
   безпосередньо, не здогадуватись з назв файлів.
5. **`git log`** — НЕ покладатися як на єдине джерело. На практиці комітів
   часто менше, ніж реально зроблено (нерегулярні коміти, робота з кількох
   комп'ютерів). Корисний лише як допоміжний якір дат.

**Головне правило: жодних вигадок.** Кожен факт у статті має простежуватись
до одного з джерел вище. Якщо джерела для якоїсь деталі немає — не
домислювати, а або лишити загальнішу фразу, або запитати користувача.

**Якщо джерело виглядає застарілим** (документація суперечить коду) — не
виправляти мовчки і не довіряти мовчки. Повідомити про розбіжність і дати
рішення, чи варто оновлювати документацію окремо (це вже інша задача, не
частина написання статті).

## Позиціонування — уточнювати щоразу, не вважати сталим

Продуктове позиціонування може змінюватись від разу до разу (наприклад: "на
даному етапі мобільний застосунок позиціонуємо тільки для водія, функції
персоналу не згадувати" — рішення станом на серпень 2026, не постійне
правило). Перед написанням циклу статей — уточнити в користувача, чи є
подібні тимчасові обмеження на цей момент.

## Аудиторія і тон

- Блог — для **потенційних клієнтів** (власники/менеджери автопарків), не
  для розробників. Жодного технічного жаргону, назв класів/таблиць, деталей
  реалізації.
- Подача — з фокусом на вигоду/проблему, яку рішення вирішує, а не на "що
  зроблено" технічно.
- `**bold**` для ключових термінів, `## ` підзаголовки, довжина — орієнтовно
  200-450 слів на статтю (менше для дрібної фічі, більше — якщо реальних
  деталей багато).

## Формат чернетки

Кожна стаття — окремий файл `YYYY-MM-DD-slug.md` у датованій підпапці
(`workspace/docs/articles/YYYY-MM-batch/`), з невеликим frontmatter-блоком:

```markdown
---
slug: some-slug
excerpt: Одне речення для прев'ю.
tags: тег1, тег2
status: published
published_at: YYYY-MM-DD
---
# Заголовок статті

Текст...
```

## Процес

1. **Розвідка** — зібрати сирий матеріал з джерел вище (доцільно через
   фонові фор-агенти, щоб не роздувати основний контекст сирим виводом).
2. **Синтез у теми** — не стаття на коміт/дрібну правку, а змістовні історії
   за фічами. Врахувати позиціонування (розділ вище).
3. **Показати список заголовків + дат на затвердження користувачу** —
   ДО написання повних текстів, щоб не писати вхолосту.
4. **Написання чернеток-файлів** (не одразу в БД) — щоб можна було разом
   переглянути й доопрацювати, з git-історією для diff.
5. **За потреби — поглиблення** — якщо перший прохід вийшов тонким/загальним,
   окремий прохід із прицілом саме на джерела з розділу вище (документація,
   реліз-ноути, код), а не додавання "води".
6. **Імпорт у БД** — одноразовою міграцією + сідером (той самий патерн, що й
   для інших одноразових перенесень даних — `App\Support\*`, викликається з
   міграції, не консольною командою), яка читає frontmatter+контент чернеток
   і записує в `blog_posts`.

## Розклад публікації

Не публікувати весь пакет статей одним днем. Змішувати:
- **Заднім числом** — заповнити реальну прогалину, дати відповідають
  орієнтовному часу, коли фіча реально вийшла.
- **Наперед** — рівномірно розподілити на найближчі тижні (наприклад, раз на
  2-3 дні), використовуючи відкладену публікацію (`published_at` у
  майбутньому, синхронізація на лендінг підхоплює автоматично).
