# Тестові дані Уклону для парку «Київ»

_Записано 2026-10-29 під час статей блогу._

Парк «Київ» (id 15) — демо-парк для статей, документації й роликів — не підключений до Уклону. Через це
частина кабінету в ньому порожня або з попередженням і не годиться для скрінів:

- «Заробіток водіїв» — «Не вдалося отримати дані з Uklon… Uklon settings not found», колонки Уклону з
  прочерками. Звіт вивірений — **код не чіпати**, проблема лише в даних.
- «Знайти в Уклоні» у формах водія й авто — «Знайдено 0» (немає флоту).
- Економіка парку/авто, бонуси брендування, замовлення — без даних Уклону.

Треба придумати, як наповнити «Київ» правдоподібними даними Уклону (вигадані водії, авто, замовлення,
заробіток) без реального акаунта Уклону і без доступу до DiDiDrive. Варіанти — обговорити:
сідер/data-міграція з демо-рядками в архівній базі Уклону; «демо-режим» налаштувань Уклону для парку.

## Обговорення 2026-10-30

- Звіти беруть Уклон із **живого API** (`UklonApiService` → `UklonCachedClient`, напр.
  `UklonDriverReportService::getDriversOrdersReport`), а не з бази — тож копія рядків з парку 1 нічого
  не дасть.
- Пропозиція: **демо-Уклон на рівні API** — позначка «демо» в налаштуваннях Уклону парку «Київ»;
  для такого парку замість `UklonApiService` — демо-клієнт з тим самим форматом відповідей (флот, водії,
  авто, звіт по замовленнях, бонуси). Звіти/пошук/економіка/синхронізація — без змін.
- Дані: варіант 1 — маскована копія парку 1 (ризик впізнання за адресами/часом/сумами, залежність від
  DiDiDrive); варіант 2 (рекомендовано) — детермінований генератор для акторів «Київ», відкалібрований
  лише середніми парку 1 (поїздок на зміну, середній чек, частка готівки, чайові, комісія).
- Перший крок — перелік викликів API Уклону в системі (≈ 9 сервісів) і їх форматів.

**Рішення 2026-10-30:** варіант 2 — мок Уклону для «Київ»: демо-клієнт API замість `UklonApiService`,
дані генеруються (детерміновано) і калібруються середніми з даних Уклону парку 1. Реальні замовлення
парку 1 не копіюємо. Робимо після статей.
