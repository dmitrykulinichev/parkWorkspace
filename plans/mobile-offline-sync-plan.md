## 0. Узгоджені рішення

**Мета:** застосунок стабільний і зручний без інтернету — водій бачить свої дані завжди,
а не порожній екран чи помилку.

1. **Екрани читають тільки локальну базу.** Мережа працює окремо й лише оновлює базу. Один
   шлях даних для онлайн і офлайн — без правила "з сервера, а з бази, якщо нема інтернету"
   (ознака зв'язку запізнюється й помиляється; два шляхи = подвійна логіка).
2. **Окремий фоновий механізм синхронізації** асинхронно оновлює базу. Напрямок один:
   сервер → база.
3. **Справжня синхронізація, не попутний кеш:** запит "що змінилося з моменту X", сервер прямо
   повідомляє про видалені записи. Бекенд доробляємо під це.
4. **Запис завжди йде на сервер** (черги відкладених дій НЕ робимо). Сервер перевіряє й
   відповідає, застосунок кладе результат у базу. Без зв'язку запис заблокований, як зараз.
5. **Критичні дії перевіряє сервер, а не база** (здача/прийом авто, перевірка пробігу).
6. **Давність видно:** якщо оновити не вдалось — "оновлено о 14:20".
7. **Один вхід у синхронізацію — "оновити сутність X".** Хто його викликає, їй байдуже. Зараз:
   запуск, повернення в застосунок, відкриття екрана, оновлення потягуванням, повернення
   зв'язку, власний запис. Пізніше — push і сокет: вони несуть лише сигнал "є зміни", а дані
   завжди йдуть тим самим запитом змін (втрата сигналу нічого не ламає, шлях даних один).
8. **Синхронізація працює, поки застосунок відкритий.** Системної фонової служби немає.
9. **Підсумки без ідентифікаторів** (плитки Головної, графік, Інфо, опції заправки) — не
   сутності: для них простий кеш "остання відповідь + час оновлення" в тій самій базі.
10. **Тільки порціями, без періодичної повної синхронізації.** Звичайний запит змін малий сам
    по собі. Велике — лише перше завантаження: сервер віддає по N записів із позначкою "є ще",
    застосунок кладе порцію в базу й питає наступну; обрив зв'язку — продовження з того ж
    місця. Глибина першого завантаження обмежена (90 днів), старіше — порціями, коли водій
    гортає історію. Повне перезавантаження — лише аварійний випадок, який вирішує сервер
    (позначка застаріла), і йде тими самими порціями. Періодична повна маскувала б помилки
    звичайної синхронізації.
11. **Порядок:** основа + одна сутність наскрізь (ручні поїздки) як експеримент → оцінка →
    решта сутностей за тим самим зразком.

## 1. Що є зараз

- Застосунок: кешу немає, кожен екран бере дані тільки з мережі (`ManualTripRepositoryImpl`
  → `ManualTripApiClient`). SQLDelight підключений у `shared/build.gradle.kts`, таблиць немає.
  Сесія відновлюється локально (запуск без інтернету працює). Форми запису без зв'язку
  заблоковані (`ui/common/connectivity/OfflineWriteGuard`). Стан зв'язку —
  `ConnectivityMonitor` (`kmp/docs/domain/connectivity.md`).
- Бекенд, ручні поїздки: `GET/POST/PUT/DELETE /manual-trips`
  (`DriverManualTripController` → `ManualTripService`). Список — сторінками, фільтр
  `date_from`/`date_to`, сортування за `date desc`.
- **Видалення справжнє** (`$trip->delete()`, без SoftDeletes): водієм, персоналом із кабінету і
  кроном `bot:sync-manual-trip-deletions` (повідомлення зникло з Telegram-чату). Тобто записи
  зникають і без участі застосунку — саме цей випадок синхронізація має покривати.
- Запиту "зміни з часу X" немає в жодному маршруті водійського застосунку. `updated_at` у
  записів є.

## 2. Бекенд

### 2.1. Журнал видалень (замість м'якого видалення)

М'яке видалення (`SoftDeletes`) на `manual_trips` НЕ беремо: таблицю читають понад 20 місць
(звіти, економіка, експорти, білінг), частина — сирими запитами `DB::table('manual_trips')`,
які `SoftDeletes` не фільтрує. Видалені поїздки потрапили б у гроші.

Натомість — окрема таблиця-журнал `sync_deletions`:

| Поле | Зміст |
|---|---|
| `entity` | тип сутності (`manual_trip`, далі — інші) |
| `entity_id` | ідентифікатор видаленого запису |
| `park_id`, `driver_id` | чий це був запис — щоб віддати лише власникові |
| `deleted_at` | коли видалено (індекс разом із `entity`, `driver_id`) |

Запис у журнал — подією моделі `deleted` (трейт `RecordsSyncDeletions` на моделі): спрацьовує
для всіх трьох шляхів видалення, жоден наявний запит не міняється. Старі записи журналу
чистяться кроном (наприклад, старші 90 днів — застосунок, що не синхронізувався довше, робить
повне перезавантаження, §2.2).

### 2.2. Запит змін

`GET /api/driver/v1/sync/manual-trips?since=<позначка>`

```json
{
  "data": {
    "upserts": [ { "id": 1, "date": "...", "amount": "100.00", "distance": null,
                   "notes": null, "source": "app", "vehicle": { ... }, "updated_at": "..." } ],
    "deleted_ids": [ 17, 21 ],
    "cursor": "2026-10-11T09:15:02Z",
    "full": false,
    "has_more": false
  }
}
```

- `since` порожній або старший за глибину журналу видалень → `full: true`: клієнт замінює все
  своє збережене вмістом відповіді (а не доповнює).
- `upserts` — записи водія в поточному парку з `updated_at >= since`, у тому самому вигляді, що
  й у списку `/manual-trips`. `deleted_ids` — із журналу за `deleted_at >= since`.
- `cursor` — час сервера на початок запиту мінус запас у кілька секунд. Клієнт зберігає його
  й шле наступного разу. Запас дає перекриття: той самий запис може прийти двічі — це безпечно,
  бо запис у базу — "вставити або замінити".
- **Порції (§0 п.10):** не більше `limit` записів за відповідь (типово 200), порядок —
  `updated_at, id`. `has_more: true` → клієнт одразу питає далі з `cursor` цієї відповіді
  (тоді `cursor` — позиція останнього відданого запису, а не час сервера). Видалені віддаються
  з останньою порцією.
- Глибина першого завантаження — останні 90 днів за датою поїздки; старіше — окремим запитом
  `before=<дата>` тією ж порцією, коли водій гортає історію далі.
- Обмеження частоти — з власним префіксом (`throttle:...,sync`), правило з `CLAUDE.md` бекенду.

- [x] `Services/Sync`: `SyncService` (єдиний вхід) + реєстр сутностей (`config/sync.php`,
      `SyncableEntity`, `Entities/ManualTripSync`) + `EntityChangeFeed` (механіка) + `SyncCursor`;
      один маршрут `GET /sync/{entity}` → `DriverSyncController@changes` (`throttle:120,1,driver-sync`).
      Рішення користувача 2026-10-11: уся синхронізація всіх сутностей — в одному сервісі Laravel.

### 2.3. Відкриті питання бекенду

- Поїздку перепризначили іншому водієві (якщо кабінет таке дозволяє) — для першого водія вона
  має зникнути: писати в журнал видалень і при зміні `driver_id`. Перевірити, чи можливо.
- `updated_at` поїздки не змінюється, коли міняється пов'язане авто (номер, модель) — у базі
  застосунку лишиться стара назва авто до наступної зміни самої поїздки. Прийнятно чи ні —
  вирішити, коли дійдемо до сутності "авто".
- Один спільний запит змін на всі сутності чи по одному на сутність — вирішити після
  експерименту (починаємо з одного на сутність).

## 3. Застосунок (KMP)

### 3.1. Локальна база

SQLDelight, одна база на застосунок. Дані розділені за акаунтом і парком (`user_id`,
`park_id` у кожній таблиці); при виході з акаунта база очищається.

- `manual_trip` — поля сутності + `user_id`, `park_id`.
- `sync_state` — для пари (сутність, акаунт, парк): позначка `cursor`, час останньої успішної
  синхронізації, остання помилка.
- (пізніше) `cached_response` — підсумки без ідентифікаторів: ключ → відповідь + час.

### 3.2. Шари

```
екран ── ViewModel ── Repository ──(читання: Flow)── локальна база
                          │                              ▲
                          └─(запис)── API ──результат────┤
                                                         │
        приводи ──► SyncEngine ── API "зміни з X" ───────┘
```

- **`SyncEngine`** (Koin `single`): `requestSync(entity)` — єдиний вхід (§0 п.7). Не запускає
  другу синхронізацію тієї самої сутності, поки йде перша; помилку мережі мовчки відкладає до
  наступного приводу. Знає список "синхронізаторів сутностей" і нічого про їхній вміст.
- **`EntitySyncer`** — інтерфейс на сутність: взяти позначку → запит змін → однією транзакцією
  застосувати `upserts`, `deleted_ids`, нову позначку. Перша реалізація — `ManualTripSyncer`.
- **`ManualTripRepository`** — читання віддає `Flow` з бази (список за день, історія); запис
  (створити/змінити/видалити) йде в API, результат одразу кладеться в базу тією ж транзакційною
  операцією, що й у синхронізатора.
- **Приводи** — в одному місці (`SyncTriggers`): запуск, повернення в застосунок, повернення
  зв'язку (`ConnectivityMonitor` → `ONLINE`), зміна парку/акаунта. Екран при відкритті й
  потягуванні викликає `requestSync` через ViewModel.
- **Давність** — `sync_state` як `Flow`: екран показує "оновлено о …", коли остання
  синхронізація не вдалась або давня.

## 4. Після експерименту

Оцінити на поїздках: обсяг коду на сутність, поведінку на слабкій мережі, чи зручний контракт
запиту змін. Тоді — решта записів водія тим самим зразком (пробіг, звернення, витрати,
заправки, авто, документи авто), потім кеш підсумків (§0 п.9), потім текст банера "відображаються
збережені дані" (`kmp/docs/domain/connectivity.md`).

## 5. Запис без зв'язку (на майбутнє, зараз НЕ робимо)

Рішення §0 п.4 лишається: зараз запис іде лише на сервер. Але сервіс синхронізації на бекенді
будується так, щоб зворотний напрямок ліг у нього ж (рішення користувача 2026-10-11):

- Застосунок зберігає дію в локальній базі (черга) і показує запис як "очікує відправки".
- `POST /sync/push` — пачка дій, кожна з унікальним ключем від застосунку.
- `SyncService` за реєстром викликає наявний бізнес-сервіс сутності; правила не дублюються.
- Ключ зберігається з записом — повтор не створює дубль. Відповідь по кожній дії окремо
  (прийнято / відхилено з причиною / потрібне підтвердження, напр. 409 `ASSIGNMENT_WARNING`).
- Лише дії "додати запис" (рука, пробіг, витрата, заправка, звернення). Здача/прийом авто,
  редагування й видалення — тільки онлайн.
