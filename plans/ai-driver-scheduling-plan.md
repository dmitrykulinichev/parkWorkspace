# AI-планування розстановки водіїв по авто

Дата: 2026-08-30. Статус: дослідження завершено, правила v1 перевірені на
реальних даних park_id=1 (DiDiDrive), реалізація ще не почата.

## Мета

Максимальне завантаження авто, мінімум простою. AI пропонує чорновий графік
на N днів вперед → адміністратор дзвонить водіям і підтверджує. AI ніколи не
призначає остаточно сам.

## Що з'ясували з даних (park_id=1, 632 записи vehicle_assignments за ~рік)

- За весь рік у більшості пар водій-авто видно короткі циклічні патерни
  (типово 2-4 дні роботи / 2-4 дні відпочинку), але це середнє по року
  змішує стабільні періоди з "періодом притирання" на початку і випадковими
  довгими викидами (одна зміна на 56 днів здатна зламати всю статистику).
- **Останні 90 днів — набагато релевантніший зріз, ніж весь рік.** У
  свіжому вікні картина інша: більшість авто зараз обслуговує ОДИН
  постійний водій (соло-стиль), а не команда з ротацією. Інші імена в
  історії — переважно одноразові тимчасові підміни.
- Водії, як правило, тримаються "свого" авто: якщо порахувати, яка частка
  ВСІХ призначень водія (за весь час, на будь-яких авто) припадає на
  конкретне авто — у "домашніх" водіїв ця частка ≥60%. Це відсіює тимчасові
  підміни від справжньої прив'язки.
- У кожного водія свій особистий ритм (медіанна тривалість зміни й
  відпочинку), порахований з ЙОГО ВЛАСНОЇ історії — не команди. Приклад:
  Оркіш Максим стабілізувався на 2 дні роботи / 2 дні відпочинку з березня
  2026, після кількох хаотичних перших тижнів.
- Дані не завжди чисті: трапляються задвоєні водії з однаковим іменем
  (звільнили-найняли заново), і поле `vehicles.driver_id` іноді не збігається
  з останнім реальним записом `vehicle_assignments` (стейл дані). Модель має
  на це зважати, а не сліпо довіряти одному джерелу.
- З 13 авто park_id=1 за останні 90 днів (лише статус `active`/`new`,
  кандидатів і неактивних не рахуємо): 4 — чіткий соло-водій, 4 — стабільна
  ротація 2-3 осіб, 4 — немає стабільного власника (забагато різних людей
  без лідера), 1 — взагалі без активності (реальний простій).

## Правила v1 (підтверджені аналізом, зашиті у видобування даних + промпт)

1. Водій, як правило, тримається "свого" авто; поява на іншому — тимчасова
   заміна, не нова постійна прив'язка.
2. Особистий ритм рахується з ПОВНОЇ історії водія, не усереднюється по
   команді. Окрім рухомого циклу "N через M" є ще два окремі стилі, прив'язані
   до календарного тижня, а не до дати останньої зміни: "лише вихідні"
   (працює тільки сб/нд) і дзеркальний "лише будні" (працює лише пн-пт,
   реальний приклад — Шестак Дмитро, 26 призначень, 4% на вихідних).
3. Соло-стиль (один водій без ротації) — нормальний і поширений випадок, не
   треба штучно підселяти когось ще.
4. Ротація між кількома "домашніми" водіями — черга йде тому, хто довше
   відпочиває ВІДНОСНО СВОГО звичного циклу (days_resting_now /
   personal_style.median_rest_days), при рівних — менше recent_90d_turns
   (баланс навантаження).
5. Немає стабільного "домашнього" водія (жоден ≥60%) або кандидати
   суперечать одне одному → НЕ вигадувати чергу, позначати
   needs_human_decision.
6. Активне зараз призначення — сильний сигнал, що той самий водій
   продовжує, поки не мине його типова тривалість зміни.
7. Авто без жодного запису за останні 90 днів (серед active/new водіїв) —
   ймовірний реальний простій, найважливіший сигнал для адміністратора.

Лише `active`/`new` статуси водіїв (у ПОТОЧНОМУ парку) беруться до уваги;
`candidate` і `inactive` — ні. Водій може одночасно бути активним одразу в
кількох парках (не тільки послідовно "перейшов" — буває й паралельно). Якщо
для парку X його статус `inactive`, це означає лише "не бере участі в
плануванні ТУТ" (можливо тому, що зараз активний в іншому парку), а не
обов'язково "звільнений". При цьому особистий стиль/портрет водія (ритм
робота/відпочинок, "домашнє" авто, тяжіння до буднів/вихідних) — властивість
людини і, як правило, не змінюється залежно від парку. Тому для побудови
портрету беремо ПОВНУ історію призначень водія без фільтра по парку, а для
відбору "хто бере участь у плануванні саме тут" — фільтруємо по
статусу+парку окремо.

Ці правила — стартова версія, будуть уточнюватись з практики (нові
винятки, нові типи причин заміни тощо).

## Формат даних для агента (контекст)

Один JSON-документ на парк, генерується перед кожним запуском:

```json
{
  "generated_at": "2026-08-30T10:00:00Z",
  "park_id": 1,
  "horizon_days": 5,
  "vehicles": [
    {
      "vehicle_id": 19,
      "license_plate": "BI5581IH",
      "currently_active_assignment": {
        "driver_id": 23,
        "driver_name": "Чумак Павло",
        "since": "2026-08-27"
      },
      "candidates": [
        {
          "driver_id": 12,
          "driver_name": "Діяконенко Антон",
          "driver_status": "active",
          "lifetime_share_on_this_vehicle": 0.63,
          "lifetime_assignments_total": 35,
          "personal_style": {
            "median_shift_days": 3,
            "median_rest_days": 2,
            "sample_size": 22,
            "confidence": "high"
          },
          "last_activity_date": "2026-07-28",
          "days_resting_now": 33,
          "recent_90d_turns": 4
        }
      ],
      "recent_history_90d": [
        { "driver_name": "Діяконенко Антон", "start": "2026-07-20", "end": "2026-07-23", "is_home_driver": true },
        { "driver_name": "Жила Юрій", "start": "2026-07-23", "end": "2026-07-24", "is_home_driver": false }
      ]
    }
  ]
}
```

Дизайн-рішення: `recent_history_90d` навмисно передає сирі факти, а не лише
готовий висновок — щоб агент міг сам щось помітити, якщо розрахунок
`personal_style`/`is_home_driver` десь помиляється.

`is_home_driver` = ≥60% усіх призначень водія (за весь час, на будь-яких
авто) припадає саме на це авто.

## Промпт

```
Ти аналізуєш дані парку таксі, щоб скласти чорновий графік розстановки
водіїв по автомобілях на найближчі {horizon_days} днів. Це ЧЕРНОВИЙ
проєкт — адміністратор парку перевірить і підтвердить його дзвінками
водіям, тому краще чесно сказати "не впевнений", ніж вигадати.

Мета: максимальне завантаження автомобілів, мінімум простою.

Правила, підтверджені аналізом історії цього парку:
1. Водії, як правило, тримаються "свого" авто. Поява водія на іншому
   авто, ніж зазвичай, — це майже завжди тимчасова заміна, а не нова
   постійна прив'язка.
2. У кожного водія свій особистий ритм роботи (скільки днів працює,
   скільки відпочиває) — він у полі personal_style. Не усереднюй по
   команді, використовуй ритм КОНКРЕТНОЇ людини.
3. Буває, що одне авто обслуговує ОДИН водій постійно, без ротації —
   це нормально, не намагайся штучно підселити когось ще.
4. Якщо авто ділять кілька "домашніх" водіїв — це черга. Пріоритет
   отримує той, хто довше відпочиває ВІДНОСНО СВОГО ЗВИЧНОГО циклу
   відпочинку (days_resting_now / personal_style.median_rest_days —
   що вище, то більше "заслужив" чергу). При приблизно рівних —
   перевагу тому, у кого менше recent_90d_turns (баланс навантаження).
5. Якщо для авто немає жодного водія з lifetime_share_on_this_vehicle
   ≥60%, або кандидатів забагато й вони суперечать одне одному —
   НЕ вигадуй чергу. Постав needs_human_decision: true і поясни чому.
6. Якщо currently_active_assignment існує — цей водій із високою
   ймовірністю продовжує, поки не мине його типова тривалість зміни.
7. Авто без жодного запису в recent_history_90d — це, ймовірно,
   реальний простій. Познач окремо, це найважливіший сигнал для
   адміністратора.

Для кожного авто визнач:
- style: "solo" (один водій без ротації) | "rotation" (черга з N
  водіїв) | "unstable" (немає стабільної команди) | "idle" (немає
  активності за 90 днів)
- якщо solo або rotation — план на кожен з {horizon_days} днів: хто
  за кермом, з якої по яку дату
- одне речення обґрунтування (чому саме ця людина/дата)
- confidence: "high" | "medium" | "low" — на основі personal_style.confidence
  і того, наскільки однозначна ситуація

Поверни JSON:
{
  "plan": [
    {
      "license_plate": "...",
      "style": "solo" | "rotation" | "unstable" | "idle",
      "schedule": [
        { "driver_name": "...", "from": "YYYY-MM-DD", "to": "YYYY-MM-DD", "reasoning": "..." }
      ],
      "needs_human_decision": false,
      "confidence": "high"
    }
  ]
}

Дані парку — нижче:
{vehicles_json}
```

## Додаткове джерело: зіставлення план/факт (DriverScheduleSlot vs VehicleAssignment)

park_id=1 має 2848 з ~2870 усіх слотів графіка в системі (`driver_schedule_slots`)
— майже повний збіг із парком, де рахувались факти вище. Це дозволяє
зіставити, хто був ЗАПЛАНОВАНИЙ на зміну (графік) з тим, хто РЕАЛЬНО
працював у той день на тому авто (vehicle_assignments), і порахувати для
кожного водія коефіцієнт відхилення від плану.

**Результат (2569 планових змін з водієм, park_id=1, весь наявний період):**
- Загальний % розбіжностей (без урахування слотів без жодного факту): **10%**
  — більшість запланованого таки збігається з реальністю.
- Розподіл дуже нерівномірний: є велика група водіїв з 0% розбіжностей на
  суттєвих вибірках (Браїлко Владислав n=109, Богдашкін Константин n=105,
  Коваленко Валентин n=70, Маляренко Вадим n=65, Янкин Андрей n=50) — для
  них план = факт майже завжди.
- Є видима "нестабільна" група з реальним відхиленням 15-30% на пристойних
  вибірках: Оркіш Максим (15%, n=111), Шишка Андрій (14%, n=122 хоч і з
  великим no_data), Чумак Павло (29%, n=14), Ткачук Андрій (23%, n=14).
- **Аномалія, що вимагає ручної перевірки, а не сліпого висновку**:
  Коротіна Ольга (n=25, 20 розбіжностей із 25 порівнянних) і Гавриш Тетяна
  (n=25, 17 із 25) показують **100% розбіжність на суттєвій вибірці**. Це
  або справді вкрай нестабільні люди, або ознака проблеми з процесом
  (наприклад, їх типово ставлять "на всяк випадок", а по факту завжди хтось
  інший підміняє) — цю гіпотезу треба перевірити з людьми, які знають
  контекст цих водіїв, перш ніж використовувати коефіцієнт як факт.
- **408 запланованих слотів взагалі не мають жодного факту призначення в
  ту дату** (авто без жодного запису assignments того дня). Це ОКРЕМА
  категорія від "розбіжності" — швидше ознака, що облік призначень не
  завжди фіксує короткі/неформальні зміни (наприклад, водій із
  довготривалим закріпленням не отримує новий запис на кожен робочий день),
  ніж доказ реальної відмови. Не змішувати з коефіцієнтом відхилення без
  додаткової перевірки.

### Ідея: накопичувальна таблиця стабільності водія

Замість перераховувати зіставлення план/факт "на льоту" щоразу (важкий
join 2569 слотів проти всієї історії призначень) — варто рахувати це
періодично (напр. нічним job'ом, як `documents:update-statuses`) і писати
в окрему таблицю накопичувальний журнал по кожному водію: дата, план,
факт (збіг/розбіжність/без даних), день тижня. Це дає дві переваги:
1. AI-агент читає вже готовий, дешевий `reliability_coefficient` замість
   важкого обчислення при кожному запиті контексту.
2. Можна рахувати коефіцієнт НЕ лише загальний, а й по днях тижня
   (наприклад, "цей водій зривається саме по п'ятницях") — саме такий
   зріз і потрібен для виявлення системи в нестабільності, а не просто
   разового відсотка.

Це прямий розвиток `personal_style` у контракті даних вище: додати туди
поле `reliability`:
```json
"reliability": {
  "planned_total": 111,
  "deviation_rate": 0.15,
  "deviation_by_weekday": { "Пн": 0.05, "Пт": 0.4 },
  "no_data_rate": 0.01,
  "note": "потребує перевірки, якщо no_data_rate чи deviation_rate аномально високі (>50%) на малій вибірці"
}
```
І восьме правило до промпту: водіїв з високим і статистично значущим
(вибірка ≥10) `deviation_rate` не варто автоматично ставити на критично
важливі "соло" слоти без резерву — а на аномалії (deviation_rate ≈100% при
пристойній вибірці) явно вказувати адміністратору як "перевірити цього
водія в системі", а не просто довіряти цифрі.
