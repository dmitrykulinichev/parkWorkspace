## Промпт

Прочитай `C:\Repository\park\workspace\user-docs2\_data\driver-schedule.md` — це технічний стаб документації.

Згенеруй на його основі маркетинговий документ для потенційних покупців і клієнтів системи Garage24.
Запиши результат у `C:\Repository\park\workspace\user-docs2\publish\` інструментом **Write** зберігаючи структуру файлів відносно `_data\` (якщо файл існує — перезаписуй).

---

### Тон і стиль

- Аудиторія: власники автопарків, диспетчери, менеджери — люди які оцінюють систему перед покупкою
- Пряме звернення на "Ви". Активні дієслова: "Керуйте", "Плануйте", "Контролюйте"
- Кожна функція — це **вирішена проблема користувача**, а не технічний опис
- Конкретика: якщо є UI-деталі (кнопка, жест, назва елемента) — використовуй їх, вони будують довіру
- Заборонено: перебільшення, вигадки, будь-що чого немає в джерелі

---

### Структура результату

**1. Заголовок**
Назва сторінки/модуля.

**2. Підзаголовок-тезис** (одне речення)
Стисла суть: що робить цей екран і яку головну проблему вирішує. Приклад: *"Керуйте розкладом вашого автопарку в режимі реального часу."*

**3. Вступний абзац** (2–3 речення)
Якщо є `## Опис` — використовуй дослівно. Якщо немає — розкрий тезис: чому це важливо для бізнесу.

**4. Скріншоти**
Прочитай `C:\Repository\park\workspace\user-docs2\_meta\nav.json` і знайди запис для цієї сторінки за полем `path` або `docFile`. Візьми всі скріншоти з поля `screenshots` — і з вкладених `modals[].screenshots`.

Розстав їх по тексту логічно:
- Скріншот типу `page` — одразу після вступного абзацу
- Скріншоти типу `tab` — поряд з відповідним розділом тексту де про них згадується
- Скріншоти типу `modal` — на початку відповідного підрозділу `###` в розділі модалок (секція 7)
- Якщо скріншотів немає в каталозі — не додавай нічого

Формат посилання — відносний шлях від розташування publish-файлу:
```
![Назва](screenshots/light/desktop/<id>.png)
```
Приклади глибини:
- `publish/tasks.md` → `screenshots/light/desktop/<id>.png`
- `publish/fleet/vehicles.md` → `../screenshots/light/desktop/<id>.png`

Не перевіряй чи існує файл фізично — шляхи підставляються середовищем на продакшені.

**5. Основна частина — можливості**
Перетвори `@doc-features` на текст який продає. Структуру обирай сам виходячи зі змісту:
- Якщо фічі природно групуються — розбий на секції з заголовками
- Якщо функціонал цільний — пиши суцільним текстом з маркованим списком
- Якщо є яскраві UI-деталі (жест, назва кнопки, конкретна дія) — використовуй: вони будують довіру
- **Всі пункти `@doc-features` мають потрапити в результат** — кожен обіграти: коротко або повно, але як перевага для користувача. Можна перефразувати, згрупувати, змінити порядок — але не пропускати жодного
- Кожна функція — це вирішена проблема, а не технічний опис

**6. Додатковий контекст** (якщо є що сказати)
З `@doc-notes` та деталей `@doc-features` — типові сценарії, поради, важливі бізнес-правила. Форму обирай довільно: абзац, нумерований список, виносна підказка.

**7. Модальні вікна** (якщо є)

У записі сторінки в `nav.json` є поле `modals[]` — список модалок з `idoc`, `docFile`, `screenshots`.

Для кожної модалки:
1. Прочитай стаб за шляхом `docFile` відносно `C:\Repository\park\workspace\user-docs2\`
2. Стаб має ті самі поля що й основний стаб: `## Опис`, `@doc-features`, `@doc-notes`

Правила генерації:
- Якщо є хоча б одна змістовна модалка — додай розділ `## Форми та дії` і під ним `###` підрозділ для кожної
- Назва підрозділу — з `## Опис` або `@doc-title` стабу модалки; якщо немає — виведи зі slug (людською мовою)
- Одразу після заголовка `###` — скріншот модалки (якщо є в `screenshots`)
- 1–2 речення: що це за форма і яку задачу вирішує
- Далі — `@doc-features` модалки у маркетинговому стилі (так само як для основної сторінки)
- Якщо `@doc-features` порожній або стаб не містить нічого корисного — пропусти цю модалку
- Прості підтвердження (delete-confirm тощо) без власних features — пропускай, не розписуй
