# Промпт: аналіз компонента → @doc-features

## Як використовувати

1. Скопіюй блок **"Промпт"** нижче
2. Заміни `[шлях до файлу]` на реальний шлях
3. Відправ Claude

Порядок обходу: модалки → таб-компоненти → сторінки без табів → сторінки з табами (оболонка).
Сторінки з табами аналізуються в останню чергу і тільки як оболонка — кожен таб окремо.

```bash
# Знайти що ще не оброблено:
grep -rL "@doc-features" resources/js/components/ | grep -i modal
grep -rL "@doc-features" resources/js/pages/
```

## Промпт

Прочитай `C:\Repository\park\app\park-react-spa\resources/js/pages/DriverSchedule/index.jsx` і сформуй JSDoc-блок для цього компонента.
Якщо потрібно — читай імпортовані сервіси щоб знайти API-ендпоінти.
Якщо JSDoc-блок вже існує — **збагачуй, не перезаписуй**:
- Наявні пункти в будь-якому полі — зберігай без змін
- Нові пункти — додавай після існуючих
- Якщо наявний пункт неточний або застарілий — залишай як є, не чіпай (тільки людина вирішує що прибрати)
- Якщо поле відсутнє — додай його повністю
- **`@doc-human` — не чіпати ніколи.** Це поле пише тільки людина. Якщо поле відсутнє — додай порожній блок: `@doc-human` з одним рядком-заглушкою `*   <!-- TODO: human description -->`. Якщо поле вже є — не чіпай взагалі.

Якщо сторінка має **таби** — описуй тільки оболонку (загальний контекст, перелік табів, спільні елементи типу хедера чи фільтрів). Функціонал кожного таба НЕ включай — таби аналізуються окремо зі своїм `@doc-tab` блоком у своєму файлі.

Запиши результат у файл інструментом **Edit** (не Write/Replace) — вставляй новий блок або точково дописуй поля. Ніколи не перезаписуй весь файл.

**`@doc-tabs`** — тільки якщо компонент містить таби:
- Перелік дочірніх табів у форматі `tab_[module]_[name] (Назва)`
- Брати з імпортів та JSX — які таб-компоненти рендеряться

**`@doc-modals`** — тільки якщо компонент відкриває модалки:
- Перелік у форматі `modal_[module]_[name] (Назва)`
- Брати з імпортів — які Modal-компоненти використовуються

**`@doc-features`** — технічний перелік всього що робить компонент:
- Стиль: іменники і номінальні фрази (`CRUD`, `фільтрація за статусом`, `підтвердження видалення`)
- Включати: всі операції, режими, стани (порожній, помилка), деструктивні дії, валідацію
- Стільки пунктів скільки потрібно для повного опису — не скорочувати штучно

**`@doc-api`** — ендпоінти які викликає компонент (GET/POST/PUT/DELETE + шлях):
- Брати з сервісів що імпортуються (`driversService`, `api.get(...)` тощо)
- Якщо ендпоінт не вдалося визначити точно — записати назву методу сервісу

**`@doc-entities`** — основні сутності з якими працює компонент:
- Перелік моделей/об'єктів даних (`Driver`, `Vehicle`, `Payment` тощо)
- Корисно для розуміння зв'язків між модулями

**`@doc-notes`** — тільки якщо є що сказати:
UX-спостереження, типові сценарії використання, маркетингові моменти, важливі бізнес-правила.
Якщо нічого такого немає — блок не додавати.

Формат блоку:

```js
/**
 * @doc-modal modal_[module]_[name]   ← для модалки
 * @doc-page  page_[module]_[name]    ← для сторінки
 * @doc-tab   tab_[module]_[name]     ← для таба
 * @doc-title [Назва українською]
 * @doc-human
 *   <!-- TODO: human description -->
 * @doc-tabs                          ← якщо містить таби
 *   - tab_[module]_[name] (Назва)
 * @doc-modals                        ← якщо відкриває модалки
 *   - modal_[module]_[name] (Назва)
 * @doc-features
 *   - ...
 * @doc-api
 *   - GET /api/[module]
 *   - POST /api/[module]
 * @doc-entities
 *   - [Model1], [Model2]
 * @doc-notes
 *   - ... (тільки якщо є)
 * @doc-screenshots [залишити якщо вже є, не додавати якщо немає]
 */
```
